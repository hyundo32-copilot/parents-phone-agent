# 2026-11-15 재테스트 이슈 진단 (Sonnet 5.5)

대상: Galaxy Z Flip5 / One UI 9.0 실기 재테스트. 설정 화면 우회로 방해금지는 복원됐고, 비행기 모드는 실패, 와이파이는 켜졌는데 "못 고쳤어요"가 떴다.

판정 요약

| 이슈 | 원인 | 확실성 |
|---|---|---|
| 와이파이 오판정 | 복원 직후 즉시 재읽기 + `isWifiEnabled`가 ENABLING 동안 false | 코드 근거로 확정 (실기 로그는 없음) |
| 비행기 모드 실패 | 미확정. 후보는 있으나 코드만으로 검증 불가 | 미확정 |
| 설정 화면 우회 결과 무시 | `tile()`이 `setSwitchInSettings` 결과를 버리고 무조건 `attempted=true` | 확정 (원인은 아니고 진단을 가림) |

## 1. 와이파이: 켜졌는데 "못 고쳤어요" (확정)

근거 체인:

1. `Restorer.restore()`는 `apply(dev)`가 끝나자마자 `reader.read(dev.key, deep)`를 한 번만 읽고 판정한다 (`Restorer.kt` 29행, 수정 전).
2. `SettingsReader.read(WIFI)`는 `wm.isWifiEnabled`를 쓴다 (`SettingsReader.kt` 41~44행). AOSP의 `WifiManager.isWifiEnabled()`는 `getWifiState() == WIFI_STATE_ENABLED`라서, 스위치를 켠 직후 전파가 올라오는 `WIFI_STATE_ENABLING` 동안은 false다.
3. 설정 화면 경로 `setSwitchInSettings`는 스위치 노드의 `isChecked`만 확인하고 BACK으로 나온다 (`AgentAccessibilityService.kt` 167~177행). 스위치 UI는 바로 켜짐으로 바뀌므로 실제 상태 폴링이 없다. 타일 경로는 `isDone`을 3초 폴링하지만 설정 화면 경로에는 그런 폴링이 없다.
4. 그 결과 `dev.expected.matches(after)`가 false → `AttemptResult.FAILED` → `CheckRunner`가 "못 고쳤어요. 아들한테 알릴게요"를 말하고 에스컬레이션 (`CheckRunner.kt` 99행).
5. 비행기 모드·방해금지는 설정값(`Settings.Global`, `currentInterruptionFilter`)이 동기적으로 바뀌어 이 문제가 안 생긴다. 가설과 일치한다.

부수 관찰 (수정하지 않음): 타일 경로는 3초 안에 켜지지 않으면 `toggleTile`이 false를 돌려 불필요하게 설정 화면 우회까지 간다. 와이파이처럼 느리게 켜지는 경우에 해당한다. 우회 쪽은 스위치가 이미 켜져 있으면 `isChecked == want`로 클릭 없이 끝나므로 이중 토글은 일어나지 않아 해롭지 않다. 화면이 한 번 더 열리는 정도라 두었다.

수정: 복원을 시도했고 키가 WIFI면 `Settle.await`로 최대 8초, 0.5초 간격으로 맞을 때까지 다시 읽는다 (`core/Settle.kt`, `Restorer.restore`). 중단 요청이 있으면 즉시 멈춘다. 실행 못 한 경우(`attempted=false`)는 기다리지 않는다. 모바일 데이터는 `Settings.Global` 값이라 이 지연이 확인되지 않아 대상에 넣지 않았다.

## 2. 비행기 모드: 원인 미확정

코드에서 확인된 사실:

- 복원 판정은 `Settings.Global.AIRPLANE_MODE_ON`을 동기적으로 읽는다. 그래서 FAILED는 지연 문제가 아니라 실제로 스위치가 안 바뀌었다는 뜻이다.
- 우회는 `ACTION_AIRPLANE_MODE_SETTINGS` 화면에서 `findSwitch`로 "비행기 모드"/"Airplane mode" 문구 노드를 찾고, 그 노드의 하위 트리 또는 부모 한 단계의 하위 트리에서 checkable을 찾는다 (`AgentAccessibilityService.kt` `findSwitch`, 수정 전 179~187행).
- 문구 노드가 제목 텍스트뿐이고 스위치가 문구 컨테이너의 형제(행의 우측 위젯 영역)에 있다면, 부모 한 단계로는 못 닿아 null이 된다. 방해금지는 문구와 스위치가 같은 컨테이너에 있어 됐다는 가설과 구조상 모순은 없다.

그러나 One UI 9.0의 실제 접근성 노드 구조는 코드에서 알 수 없고 에뮬레이터도 없다 (`vmx/kvm` 없음). 따라서 위 구조가 원인이라고 단정할 근거가 없어서 `findSwitch`의 탐색 로직은 바꾸지 않았다 (추측성 수정 금지).

확정된 결함 (진단을 가린 것):

- `Restorer.tile()`은 `service.setSwitchInSettings(...)`의 반환값을 버리고 항상 `"접근성 설정 화면 스위치" to true`를 돌렸다. 스위치를 못 찾았어도 로그에는 "실행함"으로 남아, 실기 로그만으로는 "스위치를 못 찾음 / 못 눌렀음 / 눌렀지만 안 바뀜"을 구분할 수 없었다.

수정 (진단용, 동작 변경 없음):

- `setSwitchInSettings`가 `SwitchAttempt`(ALREADY / CHANGED / NOT_FOUND / CLICK_FAILED / NOT_CHANGED)를 돌려주고, `Restorer`가 이를 방법 문구에 넣는다. NOT_FOUND와 CLICK_FAILED는 `attempted=false`가 되어 로그에 "(실행 못 함)"이 붙는다.
- NOT_FOUND일 때는 "문구 N곳 발견, 화면 전체 스위치 M개"를 함께 남긴다. 이 두 숫자로 두 후보를 가를 수 있다:
  - 문구 0곳: 설정 화면이 안 열렸거나 문구가 다르다 (인텐트·문구 문제).
  - 문구 ≥1곳, 스위치 0개: 스위치가 접근성 트리에 checkable로 안 잡힌다.
  - 문구 ≥1곳, 스위치 ≥1개: 스위치는 있는데 `findSwitch`가 문구와 연결하지 못한다. 이때 수정 방향은 문구 노드에서 조상을 한 단계씩 올라가며 그 서브트리의 checkable을 찾되, 후보가 정확히 하나일 때만 쓰는 것이다 (여러 개면 다른 스위치를 누를 위험이 있어 실패 처리).

다음 재테스트에서 비행기 모드 실패 시 앱 로그의 해당 줄 한 개로 위 셋 중 어느 쪽인지 정해진다.

## 3. 검증

- 단위 테스트 전체 통과: 105건, 실패 0 (신규 `SettleTest` 7건 포함).
- 신규 테스트는 폴링 로직(처음부터 맞음 / 몇 번 뒤 맞음 / 끝내 안 맞음 / 중단), 기본 제한 시간, 실행 여부 판정, 로그 문구를 다룬다. Android 의존 코드(`Restorer`, 접근성 서비스)는 Robolectric이 없어 단위 테스트가 불가능하며, 와이파이 수정의 실기 동작과 비행기 모드는 실기 재테스트가 필요하다.
- 와이파이 재테스트 확인점: 복원 후 앱이 "되돌렸어요"를 말하고 에스컬레이션이 안 나가는지.

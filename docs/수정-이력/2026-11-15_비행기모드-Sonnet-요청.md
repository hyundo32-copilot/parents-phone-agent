## 진단 (로그 숫자의 의미)
- `setSwitchInSettings`는 `Settings.ACTION_AIRPLANE_MODE_SETTINGS` 화면을 열고 문구 "비행기 모드"/"Airplane mode"가 있는 스위치를 찾는다 (`AgentAccessibilityService.findSwitch`).
- 결과: 문구 노드 0곳, 화면 전체 체크 가능 노드 1개. 즉 열린 화면에는 비행기 모드 문구가 접근성 트리에 노출되지 않고, 스위치는 단 1개뿐이다.
- 열린 화면이 비행기 모드 전용 페이지일 가능성이 크다 (스위치가 1개뿐이라서). 문제는 (a) 문구가 툴바 제목이라 트리에 안 나오거나 One UI 9.0에서 다른 문구로 렌더링되거나, (b) 토글 자체가 checkable 노드가 아니라 클릭 가능 행 안에 그려지는 커스텀 뷰라서 `findSwitch`가 못 찾는 것이다.
- 4초간 `waitFor`로 재시도하는데도 못 찾았으니, 화면 로딩 타이밍 문제는 아닐 가능성이 크다. 다만 창 전환 직후 트리가 비어 있는 경우를 완전히 배제하지는 말 것.

## 할 일
1. 설정 화면 스위치 찾기(`findSwitch`/`setSwitchInSettings`)를 고쳐서, 비행기 모드 페이지처럼 문구가 안 나오고 스위치가 1개뿐인 화면에서도 토글을 찾을 수 있게 한다. 검토할 방법:
   - 열린 화면에 체크 가능 노드가 정확히 1개뿐이고 문구 매칭이 실패하면, 그 1개를 대상으로 삼는다. 단, 단일 목적 설정 화면(`ACTION_AIRPLANE_MODE_SETTINGS`처럼 해당 항목 전용 페이지)을 열었을 때만 적용하고, 여러 스위치가 있는 화면(연결·무선 설정 전체 페이지)에서는 적용하지 않는다.
   - contentDescription으로도 매칭을 시도한다.
   - 스위치 자체가 checkable이 아니면, 문구가 있는 클릭 가능 행을 눌러 토글하는 경로를 추가한다.
   - 창 내용 변경 후 트리를 다시 읽는 재시도를 넣는다 (이미 있는 4초 waitFor가 부족하면).
2. 어떤 전략으로 스위치를 찾았는지(문구 매칭 / 단일 스위치 / contentDescription / 행 클릭)를 `SwitchAttempt` 진단에 남겨서 다음 재테스트 로그에서 확인되게 한다. 기존 진단 형식("문구 N곳 발견, 화면 전체 스위치 M개")은 유지한다.
3. 와이파이·모바일 데이터·방해금지 경로를 망가뜨리지 않는다. `findSwitch`는 공용이므로, 단일 스위치 폴백은 위 조건을 만족할 때만 동작하게 한다.
4. 파인더 로직을 테스트 가능한 형태로 빼서 단위 테스트를 추가한다 (단일 스위치 폴백, contentDescription 매칭, 행 클릭 경로 등). 전체 단위 테스트를 통과시키고 빌드한다 (아래 빌드 명령 참조). 빌드 전 aapt dump badging으로 versionCode=1 / versionName=0.1.0-stage1 확인.

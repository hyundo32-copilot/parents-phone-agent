# 검토 결과

## 1. 가설 검증

**결론: 가설은 대체로 타당하나, 전제 하나가 빠져 있고 "항상 FAILED"는 아니다.**

AOSP `ZenModeHelper.onSetRingerModeExternal`(AudioService가 `AudioManager.setRingerMode` 경로에서 호출)의 동작:

- DND가 **우선순위(PRIORITY) 모드**이고 SILENT→NORMAL 요청이면 → `ringerModeExternalOut = ringerModeOld`, 즉 외부 링어 모드가 SILENT로 유지된다. 재읽기 SILENT → **FAILED**. 가설과 일치.
- DND가 **알람만/완전 무음(ALARMS/NONE)** 모드이면 → 같은 호출이 오히려 **zen을 OFF로 바꾸고** NORMAL이 적용된다. 이 경우 가설과 달리 성공했을 것.
- One UI의 기본 방해금지는 우선순위 모드이므로 가설 쪽 확률이 높지만, **"08:00에 DND가 어떤 필터로 켜져 있었나"가 빠진 전제**다. 수면 모드(모드 및 루틴)가 걸어두는 DND도 보통 PRIORITY.

추가로 짚을 점:

- `AudioService.setRingerMode`는 `wouldToggleZenMode(NORMAL)`(현재 외부 모드가 SILENT일 때 참)이고 알림 정책 접근이 없으면 `SecurityException`을 던진다. 13:41에 성공했으니 권한은 있다. 다만 Restorer의 RINGER_MODE 분기에 try/catch가 보이지 않는다 — 예외가 FAILED로 기록되는지, 크래시/중단되는지 코드에서 확인 필요.
- 재읽기는 문제 아님: `setRingerModeInt`는 AudioService 락 안에서 동기 반영되므로 바로 `getRingerMode()`해도 최신 외부 값이 온다. SETTLE 대기 추가로는 해결 안 됨.
- Doze: `setAndAllowWhileIdle`로 유지보수 창이 열리고 AudioManager는 system_server 바인더 호출이라 Doze 제한 대상이 아니다. 가능성 낮음. 단 TTS 엔진 바인드가 Doze에서 느려질 수 있는데 복원 결과와는 무관.

**대안 원인과 확인법**

| 원인 | 가능성 | 확인 |
|---|---|---|
| DND(PRIORITY) 정책 묶임 (가설) | 높음 | 전체 로그에서 08:00 전후 DND 이탈 기록 유무(미뤄졌으면 없음), `adb shell settings get global zen_mode` 이력, 수면 모드/루틴 설정 시간 |

| 삼성 루틴/모드가 08:00 직후 다시 무음으로 되돌림 | 낮~중 | 모드 및 루틴 앱의 동작 시각, 로그의 재읽기 값이 VIBRATE인지 SILENT인지 |

## 2. 수정 방향 결정

**결정: (a) + (b) + (c) 조합. 핵심은 (a), (b)는 (a)가 있어야 의미 있고, (c)는 비용 거의 없이 다음 재발 때 진단을 가능하게 하므로 포함.**

- **(a)** 원인 수정. `setInterruptionFilter`는 NotificationManagerService 바인더 호출이고 화면·Doze와 무관하게 동작한다(정책 접근 권한은 사용자가 해제하지 않는 한 유지). 위험: API 경로 실패 시 폴백이 화면을 요구하므로 "API 시도 후 접근성 미룸"이라는 **2단계 상태**가 생긴다. 이 경우 미룸으로 분류해 시도 횟수에 안 세는 규칙을 유지해야 한다.
- **(b)** (a)만 하면 순서상 여전히 벨소리가 먼저라 FAILED가 1회 찍히고 다음 점검에서야 성공한다. 하루 2회 한도를 헛되이 소모하므로 순서 조정 필요. enum 순서는 UI/기존 테스트가 의존할 수 있으니 **enum은 건드리지 않고 복원 전용 정렬 함수**를 둔다. 또 DND를 OFF하면 AudioService가 내부 링어를 NORMAL로 되돌리기도 하므로, 벨소리 복원 직전에 재읽기해서 이미 정상이면 호출·카운트 없이 넘긴다.
- **(c)** DEFERRED 결과를 로그에만 남기고 카운트에서 제외. 텔레그램 에스컬레이션 대상은 아님.

(b)만 단독으로는 화면 꺼짐 상황을 못 푼다는 지적이 맞고, (c)만 단독은 원인 수정이 아니다.

## 3. 구현 계획

### 변경 파일·함수

**`SettingKey.kt`** — 변경 없음.

**새 파일 `RestorePlan.kt` (순수 함수, Android 의존 없음)**
```kotlin
object RestorePlan {
    // DND를 RINGER_MODE·VOLUME_RING 앞으로. 나머지는 enum 순서 유지.
    fun orderForRestore(devs: List<Deviation>): List<Deviation>

    sealed class DndPath { object Api; object ApiThenAccessibility; object DeferAll }
    fun dndPath(policyGranted: Boolean, blocker: String?): DndPath
    // policyGranted && blocker!=null → Api (실패 시 미룸)
    // policyGranted && blocker==null → ApiThenAccessibility
    // !policyGranted && blocker!=null → DeferAll
    // !policyGranted && blocker==null → ApiThenAccessibility(접근성만 실행됨)

    // 키별로 화면 게이트가 "전부 미룸"인지 "API 선시도"인지
    fun gateMode(key: SettingKey, blocker: String?): GateMode  // NONE / API_FIRST / DEFER
}
```

**`RestoreOutcome`** — `DEFERRED(reason: String)` 추가. 카운트 함수(`countsTowardDailyLimit`, `countsAsDeviationDay`)에서 DEFERRED 제외를 명시.

**`CheckRunner` 복원 루프**
```kotlin
for (dev in RestorePlan.orderForRestore(deviations)) {
    when (RestorePlan.gateMode(dev.key, gate.accessibilityBlocker())) {
        DEFER -> { deferred += dev.key; decidedKeys += dev.key; log(dev.key, DEFERRED(blocker)); continue }
        API_FIRST -> { /* Restorer가 API만 시도, 실패 시 DEFERRED 반환 */ }
        NONE -> {}
    }
    if (dev.key == RINGER_MODE || dev.key == VOLUME_RING) {
        if (reader.read(dev.key) == dev.expected) { log(dev.key, ALREADY_OK); continue }  // 카운트 안 함
    }
    // 기존 복원 → 재읽기 → SUCCESS/FAILED/DEFERRED 기록
}
```
DEFERRED는 `deferred`에 추가해 `lastCheckMillis` 미갱신 규칙 그대로 탄다.

**`Restorer.restoreDnd(service, apiOnly: Boolean)`**
- API 경로 실패 또는 권한 없음이고 `apiOnly`면 `DEFERRED("화면 꺼짐")` 반환.
- RINGER_MODE 분기에 `try/catch(SecurityException)` → FAILED("알림 정책 접근 없음") 기록.

**로그 문구**: DEFERRED → "{label}: 화면 꺼짐이라 잠금 해제 때 고칠게요". UI 목록은 기존 View 어댑터에 상태 한 줄 추가만.

### 단위 테스트 (추가)

1. `orderForRestore`: DND가 RINGER_MODE·VOLUME_RING보다 앞, 나머지 상대 순서 유지, DND 없을 때 원순서.
2. `dndPath` 4가지 조합.
3. `gateMode`: DND+blocker→API_FIRST, WIFI+blocker→DEFER, RINGER_MODE+blocker→NONE, blocker null→NONE.
4. CheckRunner(FakeRestorer): 화면 꺼짐 + DND API 성공 → DND SUCCESS, 벨소리 SUCCESS, deferred 비어 있음.
5. CheckRunner: 화면 꺼짐 + DND API 실패 → DND DEFERRED 로그 1건, 일일 횟수·이탈 일수 0, lastCheckMillis 미갱신.
6. CheckRunner: DND 복원 후 벨소리 재읽기 정상 → ALREADY_OK, 호출 0회, 카운트 0.
7. 카운트 함수: DEFERRED·ALREADY_OK 제외.
8. Restorer: SecurityException → FAILED, 루프 계속.

### 기존 169개 테스트 유지 조건

- `NEEDS_ACCESSIBILITY` 집합은 그대로 두고 `gateMode`가 그 위에서 판단(DND만 API_FIRST). 기존 "미룸은 카운트 안 함" 테스트는 DEFERRED가 같은 경로를 타므로 통과해야 함.

# UI 개선 브레인스토밍 요청 (Baze Claude Opus 5.5)

## 배경
- 앱: "폰 도우미" (`com.hyundo.parentsagent`) — 부모님 폰 설정이 잘못 바뀌면 원래대로 자동 복원하는 에이전트. 라이너 .EXE-THON 출품작, 1단계 프로토타입.
- 화면 구조: **한 화면에 모든 것이 다 나오는 단일 화면** (MainActivity 하나, ScrollView + LinearLayout, 레이아웃 XML·Compose 없이 코드로만 만듦). 이 구조는 유지한다 — 화면을 나누지 않는다.
- 사용자: (1) 부모님 — 연로하시고 스마트폰을 잘 못 쓰심. 큰 글씨·큰 버튼이 필수. (2) 현도(아들) — 원격에서 텔레그램 알림으로 확인하고, 가끔 Flip5 실기에서 직접 본다.

## 현재 화면 (MainActivity.kt 기준, 위에서 아래 순서)
1. **고치는 중 배너** (점검 중일 때만 표시): 노란 배경, "지금 고치는 중이에요 + 항목" + 큰 빨간 [중단] 버튼 (96dp 높이).
2. 제목 "폰 도우미" (30sp 굵게) + 부제 "폰 설정이 잘못 바뀌면 원래대로 되돌려 드려요." (20sp)
3. **준비 상태**: 접근성 서비스 ✔/✘ + (꺼져 있으면) 앱 정보 열기/접근성 설정 열기 버튼. 알림 정책 접근 ✔/✘ + (꺼져 있으면) 설정 열기 버튼.
4. **기준 상태**: 스냅샷 없으면 안내 문구, 있으면 찍은 시각·취침 시간·설정값 전 목록 (18sp 텍스트 덩어리) + [지금 이 상태를 기준으로 찍기] 버튼 (취침 시간 입력 다이얼로그 뜸).
5. **자동 복원 멈춘 항목** (있을 때만): 설명 + 항목별 [다시 자동 복원] 버튼 (초록).
6. **점검**: [지금 점검하기] (파랑), [폰이 이상해요] (주황) — 증상 입력 다이얼로그 뜸 (Liner 분류).
7. **고친 기록**: 최근 20줄 로그를 18sp 텍스트로 나열 ("M월 d일 HH:mm + 내용").
8. **대기열** (있을 때만): "아직 못 보낸 알림 N건" + [지금 다시 보내기] 버튼.
9. **데모 설정**: 데모용 임계값 단축 스위치, "장시간 통화 기준: N분 (감지는 2단계에서 동작)" 문구, DEBUG 빌드에서만 [장애 주입 메뉴] 버튼 (보라), 맨 아래 작은 글씨로 "Liner 키 있음/없음 · 텔레그램 있음/없음" 상태 줄.
- 공통 스타일 (Ui.kt): 검은 글씨, 기본 파랑(#1565C0) 버튼, 버튼 높이 최소 64dp·글씨 22sp·가로 전체, 섹션 제목 24sp 굵게, 본문 18~20sp.

## 요청: 브레인스토밍 + 개선안 제안
- **이번 라운드는 아이디어만 낸다. 코드를 고치지 말 것.**
- 한 화면·모든 정보 유지라는 전제 안에서, 다음을 브레인스토밍해서 구체적인 개선안을 제안할 것:
  1. **정보 위계**: 부모님이 가장 먼저 봐야 하는 것(지금 폰이 정상인지, 뭘 눌러야 하는지)이 한눈에 들어오게 섹션 순서·강조를 어떻게 바꿀지.
  2. **상태 한눈에 보기**: ✔/✘ 텍스트 나열 대신, 정상/주의/문제 상태를 색·아이콘·카드로 어떻게 보여줄지 (예: 상단 상태 카드).
  3. **고친 기록**: 20줄 텍스트 나열을 어떻게 읽기 쉽게 할지 (최신순·아이콘·접기 등). 부모님이 봐야 할 기록과 현도가 봐야 할 기록이 다른지도 따질 것.
  4. **버튼 정리**: 버튼이 너무 많은지, 가장 중요한 버튼(지금 점검하기·폰이 이상해요·중단)을 어떻게 더 크게/더 눈에 띄게 할지.
  5. **어르신 친화**: 글씨 크기·대비·터치 영역·말투(존댓말·짧은 문장)·음성 안내(TTS) 측면에서 빠진 것.
  6. **데모·개발용 요소 분리**: 데모 설정·장애 주입·키 상태 줄이 부모님 화면에 그대로 노출되는 게 맞는지, 어떻게 접거나 숨길지.
  7. **색·시각 디자인**: 지금 파랑·빨강·주황·초록·보라가 섞인 배색을 어떻게 정리할지 (앱 아이콘은 주황 배경에 웃는 폰+하트).
- 각 제안마다 **왜 좋은지(어떤 문제를 푸는지)**와 **구현 난이도(소/중/대)**를 함께 적을 것. 실현 가능한 것 위주로, 과한 것은 과하다고 표시할 것.
- 코드로 구현하는 방식(프로그래매틱 View 유지 vs XML vs Compose 전환)에 대한 의견도 한 절로 정리할 것 — 단, 이번 라운드에서는 코드를 건드리지 않는다.

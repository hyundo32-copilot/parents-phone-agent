### B3. CheckRunner 결과 구조가 카드 문장을 만들 정보를 주지 않는다. 계획의 `checkDone(fixed, failed)`로는 틀린 문장이 나온다

**근거**
- `CheckOutcome.Done(val summary: String)`뿐이다 (`CheckRunner.kt:14-19`). 고친 개수, 못 고친 개수, 미룸, 중단, 가족 알림 결과가 바깥으로 나오지 않는다. 계획:316의 "기존 반환 구조에 필드 추가"는 방향은 맞지만 넣을 필드가 정해져 있지 않다.
- 계획:250 "○개는 고치지 못했어요. **가족에게 알렸어요**"는 1부의 원칙("가족에게 알렸어요"는 실제로 보냈을 때만, 계획:13, 48)을 어긴다. `checkDone(fixed, failed)`에는 알렸는지가 없다. 지금 코드에서는 `familyNotified`(`CheckRunner.kt:159, 170`)로 이를 구분한다. `SendOutcome.REJECTED`면 못 알린 것이고(`CheckRunner.kt:164-166`), QUEUED도 아직 보내지 못한 것이다.
- 고친 것도 못 고친 것도 없는데 "모두 괜찮아요"가 틀리는 경우가 있다.
  - 읽지 못한 항목만 있어서 에스컬레이션한 경우: `cmp.unreadable`이 있으면 `needsEscalation()`이 참이 될 수 있다 (`CheckRunner.kt:151-162`).
  - 정책상 건너뛴 경우(밤 시간, 로밍 등 `Decision.Skip`, 횟수 제한 아님)에 이탈이 남아 있다 (`CheckRunner.kt:131-138`).
  - 미룬 경우: `deferred` (`CheckRunner.kt:173-174`).
  - 중단한 경우: `stopped` (`CheckRunner.kt:160-161`).
- 고친 것과 못 고친 것이 함께 있을 때의 문장이 계획:249-251에 없다.

**수정 방향**
- `CheckOutcome.Done`에 기본값이 있는 필드를 더한다. 기존 테스트의 `outcome.summary` 단언 7곳(`CheckRunnerTest.kt:112, 152, 183, 196, 217, 235, 300`)을 그대로 두기 위해서다.
  ```kotlin
  data class CheckSummary(
      val fixed: Int, val failed: Int,            // failed = pendingFailed.size (횟수 제한 포함)
      val deferredLabels: List<String>, val stopped: Boolean,
      val escalated: Boolean, val familyNotified: Boolean,
      val allClear: Boolean,                       // 이탈도 못 읽은 것도 없음 (= NO_PROBLEM 로그 조건, CheckRunner.kt:181)
  )
  data class Done(val summary: String, val detail: CheckSummary? = null) : CheckOutcome
  ```
- `ResultNotes.forCheck`의 우선순위는 지금 summary 분기 순서(`CheckRunner.kt:160-179`)와 같게 한다: 중단 → 에스컬레이션(알림 성공/실패) → 미룸 → 고침 → 모두 정상. "고침 n + 실패 m" 문장도 정한다.
  - 예: "점검 끝. 2개를 고쳤고, 1개는 못 고쳤어요. 가족에게 알렸어요"
  - 못 보냈으면 "… 가족에게 전화해 주세요"
- 계획:316의 `userStarted`는 CheckRunner로 보낼 필요가 없다. MainActivity의 `startCheck(trigger, …)` 콜백 안에서 이미 알 수 있고, 콜백을 넘기는 곳도 MainActivity뿐이다 (`AgentRuntime.kt:66`, `Scheduler.kt:52`, `AgentRuntime.kt:87`은 콜백 없음). 계획:316에서 `userStarted`를 지운다.
- 카드에 들어갈 범위는 아래처럼 정한다 (과제 4).
  - 카드에 나옴: 고침, 못 고침(횟수 제한 포함), 미룸("폰을 쓰는 중이라 … 잠금을 풀면 고칠게요", INFO), 중단("멈췄어요", INFO), 가족 알림 실패(FAILED).
  - 카드에 안 나옴: `ALREADY_OK`(`RestorePlan.kt:178` 문구), 앱 복귀 `ReturnReport.logLine()`(`AppReturn.kt:28`), 진단 문자열. 모두 DEV 로그에만 남긴다.
  - 계획:316에 이 목록을 그대로 적는다.

### B4. `onPause`에서 `stop()`, `onDestroy`에서 `shutdown()`을 부르면 점검의 안전 안내 음성이 같이 꺼진다

**근거**
- `Announcer`는 프로세스 전체에 하나만 있다. `AgentRuntime.init`에서 만들고 CheckRunner에 넘긴다 (`AgentRuntime.kt:33, 46-49`). MainActivity가 따로 갖는 객체가 아니다.
- CheckRunner는 고치기 전 안내 `speakAndWait(intro)`(`CheckRunner.kt:100`)를 "중단할 시간을 주는" 안전 장치로 쓴다 (위임 노트 §0).
- 계획:344처럼 `onDestroy`에서 `shutdown()`하면, 부모님이 뒤로 가기로 앱을 닫은 뒤에도 프로세스는 접근성 서비스 때문에 살아 있는데 TTS만 죽는다. 그 뒤 예약·잠금 해제 점검에서는 `tts.speak`가 계속 실패하고 3초 대기로만 동작한다 (`CheckRunner.kt:100`). 프로세스가 다시 뜰 때까지 고치기 전 안내가 나오지 않는다.
- `stop()`은 큐 전체를 비운다. 앱이 뒤로 간 순간 CheckRunner가 넣은 "아들한테 연락했어요"(`CheckRunner.kt:168`)나 "○○을 원래대로 되돌렸어요"(`CheckRunner.kt:129`)도 잘린다. 수동 점검은 접근성이 설정 화면을 열기 때문에 점검 중에 `onPause`가 반드시 한 번 일어난다.
- 계획:347의 "준비 전에 들어온 speak는 마지막 1건 보관" + `onFail` 생성자 인자 + `setLanguage` 실패 처리:
  - `setLanguage` 실패 처리는 이미 있다 (`Announcer.kt:22-25`).
  - 생성자 인자 `onFail`은 Activity가 없는 `AgentRuntime`에서 만들기 때문에 화면으로 연결할 수 없다.
  - 보관 후 나중에 말하기는 `speakAndWait`/`speak`의 "준비 안 됐으면 false" 계약을 바꾼다. CheckRunner는 false일 때 3초 대기로 넘어가므로, 이 계약이 바뀌면 안내가 늦게 나오거나 겹친다.

**수정 방향**
- 계획:344를 이렇게 바꾼다. "`onDestroy`에서 shutdown 하지 않는다(공유 인스턴스). `onPause`에서는 **[읽어 주기]로 시작한 발화만** 멈춘다." `Announcer`에 `speakOwned(text, onResult: (Boolean)->Unit): String`(utteranceId 반환)과 `stopUtterance(id)`를 둔다. 안드로이드 TTS에는 발화 하나만 취소하는 API가 없으므로, 지금 말하는 것이 내 발화일 때만 `stop()`하고 아니면 놔둔다.
- 계획:347은 "기존 `speak`/`speakAndWait`의 동작은 바꾸지 않는다"로 바꾼다. 새 함수에만 비동기 실패(`onError`) 콜백을 붙인다. 지금 `onError`는 latch만 풀어 준다 (`Announcer.kt:31-35`). `speak()`가 SUCCESS를 돌려준 뒤에 엔진에서 실패하는 경우를 잡으려면 utteranceId별 콜백이 필요하다.
- 새 메서드는 `Speaker` 인터페이스(`CheckPorts.kt:63-66`)에 넣지 않는다. 넣으면 `CheckRunnerTest.kt:30`과 `AppReturnTest.kt:211`의 Fake 두 개가 컴파일되지 않는다. 넣어야 한다면 기본 구현을 둔다. 계획:300-302 아래에 이 문장을 추가한다.

## 중요 (구현 중에 반드시 반영)

### I1. `lifecycle.currentState.isAtLeast(RESUMED)`는 이 Activity에서 쓸 수 없다
- **근거**: `MainActivity : android.app.Activity()` (`MainActivity.kt:32`). AndroidX `LifecycleOwner`가 아니라서 `lifecycle` 속성이 없다. 계획:338은 컴파일되지 않는다.
- **수정**: 계획:338을 "`onResume`/`onPause`에서 `resumed` 플래그를 관리하고, 판정은 `runOnUiThread` 안에서 한다"로 바꾼다. 앱 복귀(`returner.returnToAppWithReport()`, `CheckRunner.kt:185`)가 끝나고 onDone이 오기 때문에 대부분 이미 resumed 상태다. 그래도 창이 바뀐 직후라 `onResume`보다 먼저 올 수 있으니 실기 확인 항목(계획:379-383)에 "점검 후 복귀 직후 끝 음성이 나오는지"를 넣는다. 복귀가 `LEFT_ALONE`(다른 앱으로 감)이면 무음이 맞는 동작이다.

### I2. 시간 제한 없는 결과 카드가 상태 카드와 어긋날 수 있다 (`last_result`와 `lastResultGrade`가 따로 논다)
- **근거**: 상태 카드는 `Store.lastResultMillis/lastResultGrade`로 정해진다 (`Store.kt:31-36`, `StatusCard.kt:43-48`). 이 값은 **예약·잠금 해제 점검도 갱신한다** (`CheckRunner.kt:150`). 결과 카드는 사용자가 시작한 동작에서만 생긴다. 예약 점검에는 MainActivity 콜백이 없다 (`Scheduler.kt:52`, `AgentRuntime.kt:87`).
- **어긋나는 예**: 오후 3시 수동 점검 → 결과 카드 "점검 끝. 모두 괜찮아요"(초록). 오후 5시 잠금 해제 점검 실패 → 상태 카드는 빨강 "고치지 못했어요"인데, 바로 아래 결과 카드는 여전히 "모두 괜찮아요". 부모님은 [확인했어요]를 누르기 전까지 둘 중 무엇을 믿어야 할지 모른다.
- **수정**: 계획:230에 규칙을 하나 더한다. "`render()`에서 `note.atMillis < store.lastResultMillis`이고 점검 결과 카드이면 카드를 숨기고 지운다(`ResultNotes.isStale`)." 결과 카드는 "사용자가 방금 한 일의 응답"이고 상태 카드는 "지금 폰 상태"라고 역할을 나눈다. 백그라운드 점검 결과는 상태 카드와 "최근 고친 일"(이미 FIXED/FAILED 로그로 나옴, `CheckRunner.kt:119, 180`)로만 보인다고 계획:232에 명시한다 (과제 7의 답).
- 저장 키 이름도 헷갈린다. `last_result`는 기존 `lastResultAt`/`lastResultGrade`/`saveLastResult`와 이름이 거의 같다. 키는 `result_note`로 하고, MainActivity가 prefs를 직접 만지지 말고 `Store`에 `resultNote`/`clearResultNote()`를 두게 한다 (계획:231, 329, 333).
- [확인했어요]는 `result_note`만 지우고 `lastResultGrade`는 건드리지 않는다. 상태 카드 빨강은 다음 점검이 성공해야 풀린다. 계획:332에 이 문장을 추가한다.

### I3. "이미 점검 중이에요" 카드가 시간 제한 없이 영원히 남는다
- **근거**: 잠금 해제 점검이 도는 중에 [지금 점검]을 누르면 `AlreadyRunning`이 돌아온다 (`CheckRunner.kt:41`). 계획대로면 카드가 생긴다. 그런데 돌고 있던 점검은 콜백이 없어서 끝나도 카드를 바꾸지 않는다. 그 결과 "이미 점검 중이에요" 카드가 몇 시간 뒤에도 남는다.
- **수정**: `AlreadyRunning`은 카드로 저장하지 않는다. 진행 중임은 기존 배너(`StatusBus.fixingText`, `MainActivity.kt:85-90`)로 알린다. 고치는 중이 아닐 때는 배너가 안 뜨므로, 배너에 "점검하는 중이에요" 상태를 두는 것을 함께 검토한다 (제안 S1). I2의 stale 규칙으로도 일부 풀리지만, 저장하지 않는 쪽이 단순하다.

### I4. "가족에게 다시 보내는 중이에요"도 진행형이라 영원히 남는다
- **근거**: `flushOutboxAsync`는 결과를 돌려주지 않는다 (`AgentRuntime.kt:71-74`, `MainActivity.kt:228`). 계획대로면 보낸 뒤에도, 실패한 뒤에도 카드가 "보내는 중"으로 남는다.
- **수정**: 계획:243을 바꾼다. `flushOutboxAsync(onDone: (남은 건수) -> Unit)`로 결과를 받아 "가족에게 다 보냈어요"(FIXED) 또는 "아직 못 보냈어요. 망이 돌아오면 다시 보내요"(INFO)로 바꿔 쓴다. 범위를 넓히기 싫으면, 이 버튼은 가족 영역 안에 있으니 I5처럼 버튼 근처에 바로 피드백을 주고 결과 카드는 쓰지 않는다.

### I5. 가족·관리 영역 동작의 결과를 맨 위 카드에 띄우면 보이지 않는다. "복사했어요"는 예외로 둔다
- **근거**: 기준 저장(`MainActivity.kt:331`), 다시 보내기(228), 자동 복원 재개(296. 이건 부모님 영역 할 일 카드에도 있음, 185), 복사(381)는 화면 아래쪽(가족·관리 카드)에서 누른다. `render()`는 스크롤 위치를 그대로 유지한다 (`MainActivity.kt:108, 126`). 맨 위에 결과 카드를 넣으면 그 높이만큼 내용이 아래로 밀릴 뿐이고, 누른 사람에게 카드는 보이지 않는다. 사실상 피드백이 없어진다.
- **복사 판단**: 결과 카드로 옮길 대상이 **아니다**.
  - 현도(가족)가 쓰는 관리용 동작이고, 부모님용 카드 자리에 "복사했어요"가 남으면 부모님에게는 뜻 모를 문장이다.
  - Android 13+에서는 시스템이 클립보드 복사 확인 UI를 직접 띄운다. 이 기기 targetSdk는 36이다 (`app/build.gradle.kts`). 앱 토스트까지 띄우면 같은 알림이 두 번 나온다.
  - 권장: Toast를 지우고, 13 미만에서만 버튼 글자를 2초 동안 "복사했어요 ✓"로 바꾼다. 또는 버튼 바로 아래 작은 글로 보여 준다. 그러면 "Toast 0건" 목표도 지킬 수 있다.
- **수정**: 계획:241-246 표에 "표시 위치" 열을 더한다. 부모님 동작(점검, 증상, 자동 복원 재개)은 결과 카드에 표시한다. 가족·관리 동작(기준 저장, 다시 보내기, 복사)은 그 버튼 근처에 표시한다. 기준 저장은 1부 표에서 FIXED로 분류했는데, 설정을 고친 것이 아니므로 INFO가 맞다.

### I6. "분류: …"는 DEV라 카드를 만들 게 아니라 기록으로 보낸다
- **근거**: 계획:246·278은 DEV 카드를 만들고 `visibleOnMain`으로 숨긴다. 계획:252는 "관리용 구역이 접혀 있으면 안 보인다"고 해서 펼치면 보인다는 뜻으로 읽힌다. 서로 맞지 않는다. 게다가 분류 직후 바로 `startCheck`(`MainActivity.kt:349`)가 이어지므로, 카드로 띄워도 곧바로 점검 결과가 덮어쓴다.
- **수정**: 계획:246, 252, 278, 280을 "분류 결과는 `store.appendLog("증상 분류: …")`(DEV)로만 남긴다. 카드는 만들지 않는다"로 바꾼다. 그러면 이 토스트가 하던 "누른 뒤 뭔가 진행 중" 신호가 사라진다. Liner 분류는 망 상태에 따라 수 초 걸리므로 S1의 "점검하는 중이에요" 표시가 필요하다.

### I7. 끝 음성이 점검 중 음성과 겹쳐 세 번 말한다
- **근거**: CheckRunner는 이미 항목마다 "○○을 원래대로 되돌렸어요"(`CheckRunner.kt:124, 129`), "○○을 못 고쳤어요. 아들한테 알릴게요"(126), "아들한테 연락했어요, 잠시만 기다려요"(168)를 말한다. 계획대로 끝 음성 "점검 끝. 1개를 고쳤어요"를 더하면, 하나를 고친 수동 점검에서 같은 내용을 2~3번 듣게 된다. 호칭도 "아들한테"와 "가족에게"가 섞인다.
- **수정**: 계획:336에 규칙을 더한다. 둘 중 하나를 고르면 된다.
  - (가) 끝 음성은 고친 것도 실패도 없을 때("모두 괜찮아요")와 미룸·중단일 때만 말한다.
  - (나) CheckRunner의 항목별 결과 음성(129, 168)을 수동 점검에서는 끄고 끝 음성 한 줄로 합친다.
  - 권장은 (가)다. CheckRunner 테스트를 건드리지 않는다. 호칭 "아들한테"는 1부 원칙에 따라 "가족에게"로 바꾸는 것을 별도 항목으로 남긴다. 음성 문구만 바뀌고 테스트 단언은 없다 (`grep "아들" app/src/test` 0건).

### I8. TalkBack 분기와 announce 방식
- **감지 방법**: `AccessibilityManager.isTouchExplorationEnabled`(계획:301, 432)가 맞다. `isEnabled()`를 쓰면 안 된다. 이 앱 자신의 접근성 서비스가 늘 켜져 있어서(`AgentRuntime.kt:58-62`) 항상 true가 된다. 계획:301에 이 주의를 적는다.
- **announce**: `View.announceForAccessibility`는 API 36(Android 16)에서 deprecated다. targetSdk 36이라 lint 경고가 날 것으로 본다 (빌드로 확인하지 않음). 계획:351의 "liveRegion을 주지 않고 직접 announce"보다, 결과 카드에 `accessibilityLiveRegion = POLITE` + 카드 전체 `contentDescription`을 주고 직접 announce는 하지 않는 쪽(계획:311 안)이 낫다. 그러면 TalkBack 사용자는 카드가 바뀔 때 한 번만 듣는다. 단, `render()`가 뷰를 통째로 다시 만들기 때문에(`MainActivity.kt:109`) 새로 붙는 뷰에서 liveRegion이 동작하는지는 실기로 확인해야 한다. 안 되면 그때 announce로 대체한다.
- TalkBack이 켜진 상태에서 [읽어 주기]를 누르면 TalkBack이 버튼 이름을 읽고, 이어서 앱 TTS가 읽어 두 소리가 겹칠 수 있다. 계획:326의 결정(그래도 앱 TTS 사용)은 유지하되 실기 확인 항목에 넣는다.

### I9. [읽어 주기] 버튼 자리와 색
- **길게 누르기와의 충돌**: 없다. 길게 누르기는 가족용·관리용 `collapsible` 헤더 두 곳에만 있다 (`MainActivity.kt:234-236, 281-283`, `Ui.kt:193-210`). 상태 카드(`Ui.kt:140-157`)에는 터치 처리가 없다.
- **구조**: 지금 상태 카드는 가로 배치(큰 기호 + 글 칸)다. 버튼을 글 칸 안에 넣으면 기호 때문에 폭이 줄어 큰 글꼴에서 줄바꿈이 심해진다. 카드를 세로 바깥 상자 + 가로 줄로 바꾸고, 버튼은 카드 아래쪽에 전체 폭으로 둔다. 계획:306을 그렇게 고친다.
- **색**: 상태 카드 바탕이 초록·노랑·빨강이라, 주색 파랑 버튼(P25)은 빨강·노랑 위에서 어색하고 "색 하나에 뜻 하나"(계획:73) 규칙과도 맞지 않는다. 흰 바탕 + 검은 글씨 + 회색 테두리(manageButton 스타일)를 상태 카드 안에서만 쓰도록 명시한다.
- `contentDescription`이 "상태를 소리로 읽어 주기"(계획:308)와 "상태 읽어 주기"(계획:350)로 다르다. 하나로 정한다.

## 제안

### S1. 점검 진행 중 표시
지금은 고치는 중(`status.fixing`)일 때만 배너가 뜬다. 이탈이 없는 수동 점검은 deep 읽기로 알림 설정 화면까지 열어 수 초 걸리는데, 그동안 아무 표시가 없다. 토스트까지 없어지면 "눌렀는데 아무 일도 없다"가 된다. `StatusBus`에 "점검하는 중이에요"를 추가하는 것을 2부 범위에 넣을지 정한다.

### S2. 음성용 시각에 날짜가 빠진다
`koreanTime(hour, minute)`(계획:289)는 "어제" 같은 날짜 정보를 잃는다. 상태 카드 GOOD의 보조 줄은 `friendlyTime`("오늘 오후 3:10", `StatusCard.kt:56-69`)이고, WARN/BAD의 보조 줄은 시각이 아니라 사유 문장이다 (`StatusCard.kt:43-52`). 다음처럼 정리하길 권한다.
- `SpeechText.statusCard(state: StatusCardState, lastCheckMillis, now, zone)`: GOOD이면 "폰이 괜찮아요. 마지막 확인은 오늘 오후 3시 10분이에요.", WARN/BAD이면 "제목. 보조 줄."
- `koreanTime(millis, now, zone)`: `friendlyTime`과 같은 날짜 규칙에 "시 분" 표기.
- 결과 카드 화면 시각도 "오후 3시 12분"(계획:258)이 아니라 `friendlyTime`으로 통일한다 (기록 줄과 같은 형식). 시간 제한이 없어서 날짜가 꼭 필요하다.
- 계획:292의 `StatusLevel`은 실제 enum(GOOD/WARN/BAD, `StatusCard.kt:14`)과 이름이 맞지만, 테스트 절(계획:370)의 "정상, 경고, 기록 없음"과 3.1 #4의 OK/WARN/ERROR는 맞춰야 한다.

### S3. `forSpeech` 범위
"(3번)"을 "세 번"으로 바꾸는 규칙(계획:296)은 기록 줄을 읽을 때만 필요하다. 계획에는 기록을 읽어 주는 기능이 없다 (읽는 것은 상태 카드와 결과 한 줄뿐). 쓰이지 않는 규칙이니 빼거나, 실제로 읽는 문장(상태 카드 "!"·"✓" 기호, 결과 카드)에 필요한 치환만 남긴다. 계획:371의 "줄바꿈 → '. '"는 유지한다.

### S4. Manifest `<queries>`는 2부와 별개로 지금 바로 넣을 것 (과제 5)
- 현재 Announcer는 엔진 패키지를 직접 조회하지 않고 `TextToSpeech(context, listener)` 생성자만 쓴다 (`Announcer.kt:15`). 하지만 이 생성자는 내부에서 TTS 엔진 서비스를 찾아 바인드한다. Android 공식 패키지 가시성 문서는 targetSdk 30+ 앱이 TTS를 쓰려면 `<queries><intent><action android:name="android.intent.action.TTS_SERVICE"/></intent></queries>`를 선언하라고 안내한다. targetSdk는 36이고 Manifest에는 `<queries>`가 없다 (`AndroidManifest.xml` 전체).
- 실기 결과 문서에도 "앱의 실패 안내 TTS 여부" 미확인으로 남아 있다 (`docs/구현-검토/2026-11-14_Flip5-실기-결과.md:21`). **지금도 고치기 전 안내 음성이 조용히 안 나오고 3초 대기로만 동작하고 있을 수 있다.**
- 따라서 계획:353은 "변경 없음"을 지우고 "TTS_SERVICE `<queries>` 추가(필수)"로 확정한다. 작업 순서 9단계에서 **맨 앞(독립 단계)** 으로 옮기고, 실기에서 고치기 전 안내가 들리는지부터 확인한다. 엔진 가시성이 실제 원인인지는 실기 logcat(`TextToSpeech: Failed to bind`/onInit 상태)으로 확인해야 하며, 코드만 보고 확정할 수는 없다.

### S5. 화면 회전이나 재생성 때 결과가 늦게 반영될 수 있다
`startCheck` 콜백은 그 시점 Activity를 잡고 있다 (`MainActivity.kt:357-369`). 점검 중에 Activity가 다시 만들어지면 결과는 옛 Activity의 `showResult`로 간다. Store에 저장하면 데이터는 남지만, 새 Activity는 다음 `onResume`까지 다시 그리지 않는다. 결과 저장을 콜백이 아니라 CheckRunner 종료 경로(또는 `AgentRuntime.runCheckAsync` 래퍼)에서 하고, `StatusBus` 갱신(`StatusBus.kt:17-29`)으로 지금 Activity가 `render()`하게 하면 해결된다. 이렇게 하면 `status.idle()`(`CheckRunner.kt:141, 190`)이 이미 render를 일으키는 구조와도 맞는다.

### S6. 계획 문서의 낡은 숫자와 단계
- 계획:375 "기존 141개 … 약 155개" → "기존 218개"로 바꾼다.
- 계획:401-415의 1~4단계는 완료 표시를 하고, 6단계 선행 "1"은 의미가 없으니 지운다. B3의 "CheckRunner `CheckSummary` 추가 + 테스트"를 8단계 앞에 새 단계로 넣는다.
- 계획:390 gradle 경로는 지금도 있다 (`~/.gradle/wrapper/dists/gradle-8.10.2-bin/a04bxjujx95o3nb99gddekhwo/...` 확인). 그대로 둔다.
- 계획:377 `grep -rn "Toast" app/src/main` 0건 기준은 I5 권장안(복사 버튼 글자 바꾸기)을 따르면 그대로 지킬 수 있다.

### S7. 백그라운드 "알림으로만 결과를 알린다"(계획:441)

# UI 개선 2차 묶음 구현계획 작성 요청 (Claude Router 경유 Opus)

## 당신의 역할
부모님 스마트폰 지킴이 앱 "폰 도우미"의 UI 개선 2차 묶음에 대한 **구현계획서**를 작성한다. 코드를 직접 고치지 말고, 계획을 마크다운으로 작성해 돌려준다. 이 계획서는 나중에 구현 담당 에이전트에게 그대로 넘길 문서다.

## 앱과 현재 상태
- 앱: "폰 도우미" (`com.hyundo.parentsagent`), 안드로이드 단일 화면 앱. 부모님(70대 이상)이 쓰는 폰의 설정이 잘못 바뀌면 자동으로 되돌려 주는 앱이다.
- 화면은 코드로만 만든 프로그래매틱 View (XML·Compose 없음). `MainActivity.kt`가 `render()`로 화면 전체를 다시 그린다.
- UI 개선 1차는 완료됨: 상단 상태 카드(초록/노랑/빨강, 마지막 점검 결과 저장), 순서 재배치(상태 카드 + 큰 버튼 2개 위로), 가족·관리용 접기(2초 길게 눌러 열기), 취침 시간 선택기. 단위 테스트 141개 전부 통과.
- 현재 코드 지도 (실측):
  - `android/MainActivity.kt` — 화면 전체, `render()` + 섹션별 함수(`renderStatusCard`, `renderActions`, `renderAdmin` 등)
  - `android/Ui.kt` — 도우미: `text`, `button`, `card`, `bigButton`(높이 104dp), `statusCard`, `strip`, `collapsible`, `divider`
  - `android/Store.kt` — `data class LogEntry(val timeMillis: Long, val text: String)`, JSON 저장 키 `t`/`x`
  - `android/Announcer.kt` — TTS 안내 (지금은 고치기 전 안내에만 사용, 한국어 음성 없으면 false)
  - `android/CheckRunner.kt` — 점검 실행, 결과 저장
  - `core/StatusCard.kt` — 상태 등급 순수 함수 + 테스트, `core/LongPressGate.kt` — 길게 누르기 상태 전이 순수 함수 + 테스트
  - 토스트 사용처(`MainActivity.kt`): "다시 보내는 중이에요", "다시 자동으로 고칠게요", "기준을 저장했어요", "분류: …" 등 (전부 `Toast.LENGTH_LONG`)
  - 테스트 파일 13개, 총 141개 테스트

## 2차 범위 (이것만 계획한다)
아래는 브레인스토밍 제안서의 2차 묶음(우선순위 4·5·7번)이다. 각 항목의 원문 요약을 그대로 따른다.

**4번: 기록 분리 (P7·P8) — 난이도 중**
- P7: "고친 기록"을 부모님용 요약과 현도용 전체 로그로 나눈다.
  - 부모님용: "무엇을 / 고쳤는지 못 고쳤는지"만. 예: "✓ 오늘 오후 3:10 — 와이파이를 다시 켰어요", "✕ 오늘 오후 3:10 — 비행기 모드를 못 고쳤어요. 가족에게 알렸어요". 부모님 영역에는 최근 3~5건만.
  - 현도용: 지금 로그 그대로(전·후 값, 복원 수단, 진단 문구, QUEUED 같은 상태값, 기준 찍기·멈춤 해제 이벤트). 관리 영역에 전체 20건(접힘).
  - 구현 방향 2가지: (가) 저장 형식 그대로 두고 화면에 보일 때 문자열 규칙으로 번역("(성공)"이면 ✓ 등) — 빠르지만 문구가 바뀌면 깨짐. (나) `LogEntry`에 `kind`(FIXED/FAILED/INFO/DEV)와 `parentText`(부모님 문장) 추가 — 정석이지만 저장 형식 변경이라 기존 기록 호환(필드 없으면 DEV 취급) 필요. 제안서는 1단계 출품용으로 (나)를 권했다. **둘 중 하나를 골라 이유와 함께 적고, 호환 처리 방법을 구체적으로 적을 것.**
  - 배경: 지금 기록은 "이미 2회라 더 되돌리지 않았습니다" 같은 개발자 문장이 4번 반복돼 부모님은 폰이 크게 고장난 줄 안다.
- P8: 같은 문장 연속 반복은 표시할 때만 한 줄로 묶는다 ("… (4번)"). 저장은 그대로.

**5번: 큰 타일 버튼 + 색 정리 + 카드 (P12·P25·P26) — 난이도 소~중**
- P12: 핵심 버튼 2개([지금 점검하기], [폰이 이상해요])를 큰 타일 버튼으로. 높이 96~120dp, 글씨 26~28sp, 둥근 모서리, 아이콘+두 줄 문구. 가로 반반이 아니라 **세로로 하나씩 전체 폭** (Flip5 펼친 화면에서 반반이면 버튼이 좁아 글이 깨짐). `Ui.button`에 크기 인자를 추가하는 수준.
- P25: 색에 뜻을 하나씩만. 현재 7색(파랑·주황·빨강·초록·회색·보라·노랑)이고 뜻이 일정하지 않음. 정리안: 주 버튼은 짙은 파랑(`#1565C0` 유지, 대비·혼동 측면에서 안전) 또는 깊은 주황(`#E8590C` 계열) 중 하나를 고른다. 상태 3색은 초록 `#2E7D32` / 노랑 `#F9A825` + 검은 글씨 / 빨강 `#C62828`로, 상태 카드와 [중단]에만 쓴다. 관리 영역 버튼은 전부 회색 테두리 버튼(흰 바탕+진회색 글씨)으로 낮추고 보라·초록 버튼 제거. **두 주색 후보 중 하나를 골라 이유를 적을 것.**
- P26: 구역마다 흰 카드(둥근 모서리 16dp, 얇은 테두리)로 묶는다. `Ui.card()` 도우미가 이미 있으니 재사용한다.

**7번: 결과를 토스트 대신 카드+TTS로 (P19·P20) — 난이도 소~중**
- P19: TTS 활용 넓히기. (소) 상태 카드 길게 누르기 또는 카드 옆 [🔊 읽어 주기] 버튼 → 카드 문장 읽기. (소) 점검이 끝나면 토스트만 띄우지 말고 결과 한 줄을 읽어 준다. (과함, 제외) 화면 전체 TTS — 시스템 TalkBack이 이미 한다. 각 뷰에 `contentDescription`을 잘 다는 정도만. 주의: 한국어 음성이 없으면 `Announcer`가 false — 그럴 때 화면 문구만으로 충분해야 한다.
- P20: "기준을 저장했어요", "분류: …" 등 결과가 토스트로만 나오는 것을 상태 카드 보조 줄이나 결과 카드에 다음 점검 전까지 남긴다. 토스트(`LENGTH_LONG` 3.5초)는 어르신이 다 못 읽는 경우가 많다.

## 계획서에 반드시 들어갈 것
1. 항목별 설계 결정: 위에서 "골라 적을 것"이라 한 P7 (가)/(나) 선택과 P25 주색 선택을 결론 내리고 이유를 적는다. 그 외 모호한 점(예: 부모님용 요약 문장 규칙, 결과 카드가 보여 주는 기간, TTS 읽기 버튼 위치)도 결정을 내려 적는다.
2. 파일별 변경 목록: 새로 만드는 파일, 고치는 파일, 각 파일에서 무엇을 바꾸는지 (함수·필드 이름 수준까지).
3. 테스트 계획: 새로 추가할 단위 테스트 (순수 함수로 뺄 수 있는 로직은 `core/`에 두고 테스트를 붙인다 — 1차의 `StatusCard`/`LongPressGate` 방식). 기존 141개 테스트 유지 조건.
4. 검증 순서: 빌드·테스트 명령과 환경 주의사항 — Gradle 래퍼(`./gradlew`)는 샌드박스에서 SSL 문제로 실패하므로 캐시된 바이너리(`/home/hatch/.gradle/wrapper/dists/gradle-8.10.2-bin/a04bxjujx95o3nb99gddekhwo/gradle-8.10.2/bin/gradle testDebugUnitTest assembleDebug --offline --no-daemon`)를 쓰고, `LC_ALL=C.UTF-8 LANG=C.UTF-8`을 설정하고, "Timeout waiting to lock journal cache"가 나면 `gradle --stop` 후 재시도한다. APK 서명은 프로젝트 내 고정 키(`app/debug.keystore`)를 건드리지 않는다.
5. 작업 순서: 항목 간 의존 순서 (예: P7 저장 형식 변경이 먼저인지, P26 카드가 P12보다 먼저인지).
6. 위험과 주의: 실기 확인이 필요한 항목 (삼성 글꼴에서 ✓/✕/🔊 기호 표시, 시스템 글꼴 최대 크기에서 잘림 여부, TTS 한국어 음성 유무), 되돌리기 어려운 변경 (저장 형식 변경).

## 범위 밖 (이번 계획에 넣지 말 것)
- 3차: P14 증상 고르기 버튼, P13 중단 버튼 크기 통일, P15~P18 글씨·대비·말투 정리
- 보류: P5 기준 표, P24 빌드 정보 줄
- 하지 않음: P28 다크 모드, P29 커버 화면 전용 배치, 화면 전체 TTS, 비밀번호 잠금, 항목별 그림 아이콘
- Compose·XML 전환 금지. 코드 기반 View 유지. 커밋·푸시는 구현 담당이 하지 않는다 (계획서에 적지 않아도 됨).

## 출력 형식
- 한국어로 작성한 마크다운 계획서. 제목, 개요(2차 범위 한눈에), 항목별 설계 결정, 파일별 변경 목록, 테스트 계획, 검증 순서, 작업 순서, 위험과 주의 순으로 구성한다.
- 길이는 충실하게, 불필요한 반복은 없이. 코드 조각이 필요하면 짧게 인용한다.
